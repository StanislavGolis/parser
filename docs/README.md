# Dredger — техническая документация (v6)

> Dredger — архив // отбор // доступ: медиа-архив, который парсит медиа с разделов
> форума (2ch), скачивает и архивирует в объектное хранилище S3 (Timeweb Cloud),
> каталогизирует и публикует на сайте — каталог «досок» → треды → файлы с
> техпанелью, новинки, топ, поиск, аккаунты, **метки** («отличный контент»,
> наш аналог лайка) и премиум-подписка. Тёмный «технический» интерфейс.
>
> Один документ: статус, архитектура, модули, доступ, БД, API, эксплуатация.
> Дизайн-спека: [`DESIGN.md`](DESIGN.md) · Деплой: [`../DEPLOY.md`](../DEPLOY.md) ·
> шаблоны окружения: `.env.example`, `.env.prod.example`, `web/.env.example`.

---

## 0. Быстрый старт

```bash
cp .env.prod.example .env      # заполнить S3_* и ADMIN_TOKEN
docker compose -f docker-compose.prod.yml up -d --build
# сайт: http://localhost:80     админка: http://localhost/admin (токен из .env)
```

Разработка без контейнеров: `postgres`/`redis` в Docker, API —
`uvicorn src.api.main:app --reload`, парсер — `python src/main.py`,
фронт — `cd web && npm run dev`.

## 1. Текущий статус

**Реализовано**

*Парсинг и хранение*
- [x] Парсер 2ch (JSON API): полный и инкрементальный цикл, `parse_mode` доски
      (`all` — все новые треды, `selected` — только включённые вручную), очередь по
      `sort_order`, фильтры размера/разрешения/MIME, поиск по `md5` из API.
- [x] **Идемпотентность повторных проходов**: файл, уже сохранённый в этом треде,
      пропускается (`[have]`), запись без объекта в S3 дозакачивается и обновляется,
      строка-дубль (`duplicate_of_id`) создаётся только для файла из другого
      треда/доски (объект в S3 переиспользуется). Конфликт **SHA-256** (CDN
      пережимает картинки — один контент под разными `md5`) тоже становится
      строкой-дублем: без этого INSERT падал на `UNIQUE(media.file_hash)` и тред не
      мог пройти полный прогон. Запись файла идёт в SAVEPOINT, ошибка одного файла
      не роняет тред, а в конце треда печатается сводка `[done]`
      (saved/have/dup/invalid/filtered/err).
- [x] **Двухфазный цикл и очередь докачки**: фаза A — каталоги всех парсируемых
      досок (1 запрос на доску), фаза B — загрузка по очереди из БД
      (`pending_scan`): свежие изменения вперёд, затем LRU; очередь переживает
      перезапуск, `PARSE_CYCLE_BUDGET_MINUTES` ограничивает цикл, доски чередуются
      (round-robin) — одна доска с длинной очередью не держит остальные.
- [x] **Гигиена обхода**: `misses`/`missing_since` — тред гасится только после
      `DEAD_THREAD_AFTER_MISSES` промахов каталога (обрезанный каталог 2ch больше не
      «убивает» живые треды); `STALE_SCAN_HOURS` — плановый догон; метрика
      «Недокачано» (`files_detected` без файлов, отброшенных правилами размера).
- [x] **Инкрементальный проход и итог скана**: частые сканы по причине «изменения»
      обрабатывают только посты новее `last_post_num` (горячие треды не
      перебираются целиком), а плановый догон, «недокачано», «вручную» и первый
      проход идут полным обходом; сбой (`last_scan_errors > 0`) делает следующий
      проход полным. Итог прохода («новых 12, уже было 319, дублей 3, битых 5,
      отфильтровано 24, ошибок 1») хранится в `last_scan_note` и виден в строке
      треда в админке — разбор недокачки не требует чтения логов.
- [x] **Параллельные загрузки**: `MAX_PARALLEL_DOWNLOADS` (дефолт 2) — файлы
      качаются пачками (замер на пачке 11 МБ: ~1.8× быстрее), а валидация, S3,
      деривативы и запись в БД остаются последовательными (одна сессия);
      `PREFETCH_MAX_BYTES` (64 МБ) ограничивает память, крупные файлы качаются по
      одному. Дедупликация выполняется до скачивания, поэтому в сеть уходят только
      отсутствующие файлы.
- [x] Коммит БД после каждого треда **и каждые `DB_COMMIT_EVERY_FILES` файлов
      внутри треда** (дефолт 25): частичный прогресс виден сайту сразу, сбой теряет
      максимум пачку; кнопка «Остановить» коммитит уже скачанное.
- [x] S3 (Timeweb Cloud, приватный бакет, path-style): загрузка оригиналов,
      стриминг через API-прокси, reconciliation БД ↔ S3, очистка мусорных объектов.
- [x] Деривативы (Pillow/ffmpeg): `thumb` (~400px WebP), `thumb_blur` (размытый
      превью для премиума), `web` (~1600px WebP), `video` (720p H.264 faststart),
      постер и длительность видео; бэкфилл старых файлов — один запуск проходит всю
      очередь пачками, прогресс «осталось N из M».

*API и сайт*
- [x] FastAPI: публичные роуты (boards / threads / media / feed / top / search),
      статистика просмотров и скачиваний (дедуп по IP), rate limiting на Redis,
      пересчёт popularity.
- [x] Next.js 14: `/` (каталог досок), `/new`, `/top`, `/board/{slug}`, `/search`,

- [x] Дизайн-система Dredger (бывш. SLUICE): токены, JetBrains Mono / Inter,
      админка в токенах.

*Аккаунты и доступ*
- [x] Аккаунты (`users`/`sessions`): PBKDF2-пароли, httpOnly-сессия `sid` (30 дней),
      `/auth/register|login|logout|me` (+ счётчик меток в профиле).
- [x] Матрица ролей: **аноним** — только просмотр (лента/топ/поиск, включая
      размытые превью премиума); **зарегистрированный** — метки,
      размытые превью премиума; **премиум** — премиум-разделы, скачивание,
      оригиналы. Скачивание и оригиналы (`/raw`, `/download`) — только премиум
      (аноним → 401, без подписки → 403).
- [x] **Метка** («отличный контент») — единая пользовательская отметка (аналог
      лайка): переключатель на карточке и в lightbox (плюс пробел при просмотре),
      счётчик `media.marks_count`, вес в индексе популярности, сортировка
      `sort=marks` и личный список «мои метки» — страница `/marks`
      (`GET /api/v1/marks`; старый `/favorites` редиректит). Требует аккаунт.
      Отдельного «избранного» больше нет: оно объединено с метками
      (миграция `p1q2r3s4t5u6`).
- [x] **Премиум-доступ**: `boards.is_premium` закрывает все свои треды,
      `threads_state.is_premium` — отдельный тред, `media.is_premium` —
      денормализованный признак для отдачи. Полные версии (`thumb`/`web`/`video`)
      и оригиналы — по подписке (403 без неё), публично отдаётся **размытое**
      превью (`thumb_blur`); при активной подписке блюр снимается, бейдж
      переключается с замка на звезду.
- [x] `users.premium_until` + промо-активация премиума на 1 день из профиля
      (платёжного шлюза пока нет).

*Админ-центр (`/admin`)*
- [x] **Вкладки-разделы**: `/admin` (обзор: цифры архива, парсер, кэш), `/admin/content`
      (центр управления контентом: разделы, форум, треды, хранилище, парсер),
      `/admin/stats` (посещаемость и поведение) и `/admin/users` (аккаунты, подписки,
      блокировки, аудит). Вкладки — отдельные адреса (ссылка шарится, F5 не сбрасывает);
      гейт по admin-токену один на всю панель (`app/admin/(secure)/layout.tsx`),
      а служебная `/admin/reset` из письма остаётся вне гейта. Раздел закрыт от индексации.
- [x] **Своя аналитика посещаемости** (`page_hits` + `POST /api/v1/hit`): посетители и
      визиты (cookie `dv_sid`, пауза 30 мин), просмотры страниц, источники (реферер
      хостом + utm), устройства/браузеры/ОС, события интерфейса (просмотр файла, фильтры,
      скачивание, метки, клик по «новое с визита»), топ файлов и разделов, ошибки API

      не попадают; ретеншн чистит сырые посещения (`ANALYTICS_RETENTION_DAYS`).
- [x] **Управление пользователями**: список с агрегатами (метки, просмотры, скачивания,
      последний вход, активные сессии), карточка со следом сессий (хеш IP, User-Agent,
      когда был) и историей меток/скачиваний, действия — премиум на срок, блокировка,
      снятие всех сессий, ссылка смены пароля письмом (публичная страница
      `/reset-password` + `POST /api/v1/auth/reset`), удаление аккаунта. Все действия
      администраторов пишутся в `admin_audit` (кто, что, когда).
- [x] «Мои разделы»: кнопка «Треды» перед «Парсить», переключатели `Парсить` /
      `published|unpublished` / `FREE|PREMIUM`, переименование, удаление (БД + S3),
      статистика, ▲/▼ очередь, прогресс парсера (опрос 1 с).
- [x] **Вход в админку**: по email+паролю (админ-аккаунты из `ADMIN_EMAILS`) или по
      `ADMIN_TOKEN`; восстановление пароля — ссылкой из письма (SMTP), командой на
      сервере (`python -m src.cli.admin set-password`) либо токеном из `.env`.
- [x] Управление тредами: чипы-фильтры (Все / В работе / Парсить / published /
      PREMIUM / **В очереди** / **Недокачано** / **Просроченные** / **Мёртвые** /
      Без настроек), поиск, массовые операции (вкл/выкл парсинга, показа, PREMIUM,
      **«Вернуть в обход»**, **«В очередь»**), «Сканировать треды»
      (каталог + `?deep=true` — глубокая оценка файлов через `res/{id}.json`).
      В строке треда: причина очереди, дата последней попытки, у мёртвого — дата
      исчезновения и число промахов, у просроченного — «попытка: …».
- [x] **Удаление отдельных тредов с файлами** (в строке треда — «удалить»,

      (включая деривативы thumb/web/video и локальный кэш), метки/просмотры
      уходят каскадом. Объекты, на которые ссылаются файлы других тредов
      (перекрёстные дубли), не удаляются — их число показывается отдельно.
      Перед удалением — прикидка (`?dry_run=true`): «Файлов: N, объектов в S3: M».

- [x] «Доски форума»: полный список 2ch из `index.json` со статусами; добавление

- [x] Добавление раздела: принимает `hc`, `/hc` и ссылку (`https://2ch.su/hc/`);

      раздел появится в списке с бейджем «каталог недоступен» и не парсится.
      Причина различается: раздел есть в `index.json`, но каталог отдаёт 500
      «Not found» (закрытые взрослые разделы `/h`, `/ho`, `/hc`, `/e`, `/hg` —
      без pass форум их не отдаёт; сами доски 2ch переехали на `2ch.su`, а
      `index.json` продолжает их перечислять).
- Разведка закрытых разделов (проверено 12.09.2026): из 163 досок **14 не отдают
  каталог** (500 «Not found») — вся категория «Взрослым» (`/e`, `/hc`, `/h`, `/ho`,
  `/ga`, `/fur`, `/fg`, `/fet`, `/nf`), «Пользовательские» (`/ya`, `/r34`, `/hg`) и
  `/vn`, `/ruvn`. Не помогли: cookie-сессия и Referer браузера, альтернативные
  эндпоинты (`1.json`, `threads.json`, `/api/*`, `/mobile/*`, `/<board>/pass`),
  `?pass=`, зеркала (`2ch.org` — так же, `2ch.life` — 403, `2ch.pm` — мёртво) и
  заход с зарубежного IP (получена та же страница «Not found»). Платный пасскод
  (маркет 2ch) по их же тексту «не даёт доступов к скрытым разделам». В `index.json`
  доски остаются, поэтому названия в панели видны, но каталог парсить нельзя.
  Контент этих разделов частично сохранился в веб-архиве (Wayback: `2ch.su/hc/1.json`,
  `/e/7.json` — тот же JSON-формат, что читает парсер; выборочно в архиве ~20 % файлов,
  включая оригиналы), но это исторический срез, а не живой раздел.
- [x] «Оптимизировать медиа»: бэкфилл деривативов с автопродолжением пачками.
- [x] **Кэш медиа на диске** (`MEDIA_CACHE_*`): S3 у провайдера отдаёт ~3 МБ/с,
      диск — 500+ МБ/с. Кэшируются и премиум-оригиналы (права проверяет API),
      LRU по лимиту 40 ГБ, прогрев кэша из админки, бесплатное наполнение из
      парсера. Замер: повторная отдача 1 МБ — 163 МБ/с против 2.1 МБ/с из S3.
- [x] «Очистить S3» (объекты без записей в БД), «Сбросить всё».

*Инфраструктура*
- [x] Docker Compose (postgres, redis, migrate, parser, api, web, nginx) +
      Alembic-миграции на старте; nginx кэширует деривативы на диске
      (`X-Cache-Status`, immutable, `slice` для видео).
- [ ] Прод-деплой на VPS (домен/SSL/выкатка) — **не выполнен**, см. §8.

**Особенности и нюансы (важно для эксплуатации)**
- Счётчики «скачано / в хранилище / видимых / в каталоге» **не учитывают
  дубли-ссылки** (`duplicate_of_id`) — они совпадают с тем, что показывает сайт.
- «Скачано» в статистике доски — это `download_status='downloaded'` (скачано
  локально и **ещё не выгружено** в S3); при работающем S3 смотреть надо «В S3».
- Публичный список тредов показывает только треды, где есть хотя бы один видимый
  файл (пустые карточки-мусор скрыты), поэтому тред появляется на сайте после
  первого коммита своих файлов.
- Премиум-варианты отдаются с `Cache-Control: private, no-store` и в дисковый кэш
  nginx не попадают (иначе файл утёк бы анонимам); публичный `thumb_blur`
  кэшируется надолго.
- Legacy-медиа без `thumb_blur` (до прогона «Оптимизировать медиа») отдаются
  публично как обычное превью + клиентский blur.

**Ограничения и открытые задачи**
- Прод-деплой (домен, SSL, ротация `ADMIN_TOKEN`) — не выполнен.
- Оплата премиума не подключена: активация промо-бесплатная (1 день, продлевается).
- Старые ключи Backblaze, попавшие в git-историю, нужно отозвать и
  вычистить историю (`git filter-repo`, см. `DEPLOY.md`).
- Выкатка «Убрать дубли» из админки — при необходимости повторить чистку
  данных на других инсталляциях (одноразовый SQL в `DEPLOY.md` §Диагностика).

## 2. Архитектура

Один VPS, один Docker Compose-стек: `postgres`, `redis`, `migrate`, `parser`,
`api`, `web`, `nginx`. Наружу открыт только хост-nginx (80/443, TLS Let's Encrypt →
редирект на HTTPS), он проксирует на контейнер `nginx` (порт `HTTP_PORT`, в проде
`8080`), тот — на `api` и `web`.

| Сервис | Роль | Образ |
|---|---|---|
| `nginx` | точка входа: `/api/*` → api, `/` → web, дисковый кэш деривативов | `nginx:1.27-alpine` |
| `api` | FastAPI (публичные + админ + auth) | `parser-backend:local` |
| `parser-dvach` | прогон источника 2ch (`PARSER_SOURCE=dvach`) | `parser-backend:local` |
| `parser-slivach` | прогон источника slivach (`PARSER_SOURCE=slivach`) | тот же образ |
| `migrate` | `alembic upgrade head`, затем завершается | `parser-backend:local` |
| `web` | Next.js 14 (SSR + статика) | `parser-web:local` |
| `postgres`, `redis` | БД и состояние/лимиты/прогресс | официальные образы |

Код `api`, `parser` и `migrate` — **общий образ** `parser-backend:local`
(`build:` объявлен только у `api`). Отсюда важный нюанс деплоя: `up -d --build parser`
код не пересобирает — см. `DEPLOY.md` §Диагностика.

**Поток парсинга.** Демон (`src/main.py`) идёт **по реестру источников**
(`sources`): у каждого свои флаги прогона (`parser:{code}:enabled|up|alive|current|progress`)
и свой цикл. Цикл источника: доски с `parse_enabled` (`boards.source_id` = источник)
→ адаптер читает каталог (`catalog.json` у 2ch, список записей у сайта) → для
изменившихся тредов файлы → фильтрация → скачивание → валидация → S3 → деривативы
→ запись в БД. Каждый прогон открывает и закрывает запись в `parse_runs`
(статус `ok`/`stopped`/`error`, сводка), поэтому в админке видно, что и когда
делал каждый источник. Прогресс пишется в Redis (у `dvach` дублируется в старые
ключи, пока панель не перешла на реестр), админка его опрашивает (1 с — прогресс,
2 с — сводка).

**Источники контента (мульти-источники).** Проект переводится на несколько
источников: 2ch.hk остаётся источником `dvach`, к нему добавляется `slivach`
(`slivach.com`). Реестр источников живёт в таблице `sources` (базовый URL, тип
адаптера, `config` JSONB, расписание, лимиты, бюджет прогона), доски привязаны к
источнику (`boards.source_id`), у прогонов есть своя история (`parse_runs`).

Правила, на которые опирается вся дальнейшая разработка:
- **прогоны независимы**: у каждого источника свои ключи `parser:{code}:…`
  (`enabled`, `up`, `alive`, `current`, `progress`), свой интервал и лимиты,
  своя очередь; пауза/падение одного не затрагивает другой (целевое состояние —
  отдельный контейнер на источник, один и тот же образ);
- **треды источника** опознаются парой (доска, `external_id`): у 2ch это номер
  треда, у сайтов — слаг записи (`alena-omovich-sliv`);
- **адаптер на источник**: HTTP/парсинг источника отделён от общего конвейера
  (скачивание → валидация → S3 → деривативы → БД), поэтому новый сайт — это
  адаптер + запись в `sources`, а не копипаста парсера;
- **контент в админке разделён по вкладкам источников**, реестр отдаёт
  `GET /api/v1/admin/sources` (настройки, состояние прогона, объёмы, история).

Маппинг сайта в нашу модель (пример `slivach.com`): **категория → раздел
(«доска»)** (`/board/modeli`), **запись-«слив» → «тред»** (галерея ~80 файлов,
имя, счётчик из `<title>`), элементы записи → файлы. Особенности источника:
у видео обязателен заголовок `Referer` (иначе 403), оригиналов на сайте нет
(максимум — webp ~810–2000 px и mp4), md5 отсутствует (дедуп: `md5(url)` до
скачивания + SHA-256 после). Разведка источника: `dredge-backups/probe_slivach*.sh`.

**Поток отдачи медиа.** Клиент запрашивает `/api/v1/media/{id}/asset/{kind}` →
nginx (кэш на диске) → api (кэш на диске) → S3 (поток, без буферизации) → клиент.
Оригинал (`/raw`, `/download`) — только с сессией, премиум-варианты — только с подпиской.

**Ключи в Redis**

| Ключ | Назначение |
|---|---|
| `parser:up` | демон парсера жив (heartbeat, TTL 60 с) |
| `parser:enabled` | парсинг включён (`1`/отсутствует) |
| `parser:alive` | парсер активно работает прямо сейчас |
| `parser:current_board` | slug текущей доски |
| `parser:progress` | JSON прогресса: `phase` (catalog/files), `thread_id`, `files_total`, `files_done`, `updated_at` |
| `parser:{code}:enabled` | прогон источника включён (свой флаг у каждого: `parser:dvach:enabled`, `parser:slivach:enabled`); старые ключи без префикса читаются как флаги источника `dvach` (`src/services/sources.py`) |
| `parser:{code}:up` / `:alive` / `:current` / `:progress` | живость, текущий раздел и прогресс **этого** источника — прогоны независимы и не перезаписывают состояние друг друга |
| `backfill:variants` | JSON статуса бэкфилла: `status`, `total`, `done`, `remaining`, `processed`, `errors`, `batch_size` |
| `scan:board:{slug}` | JSON статуса «Сканировать треды» (можно ставить `deep`) |
| `board:catalog_error:{slug}` | JSON `{text, at}` — каталог раздела не читается (2ch отдал 500/404: доска удалена); TTL 6 ч, снимается успешным чтением |
| `media_cache:warm` | JSON прогресса прогрева дискового кэша: `status`, `done`, `total`, `failed`, `ts` |
| `rl:api:*` | rate limiting JSON-запросов по IP (окно 60 с, `API_RATE_LIMIT`) |
| `rl:media:*` | отдельный лимит медиа-файлов по IP (окно 60 с, `MEDIA_RATE_LIMIT` — превью в галерее иначе «съедали» общий лимит и отдавали 429) |

**Кэш nginx** (`proxy_cache_path … keys_zone=media_cache`, `max_size=20g`,
`inactive=30d`): кэшируются только `/api/v1/media/{id}/asset/*`; видео — через
`slice 1m` (Range-запросы). `/view`, `/download`, `/raw` не кэшируются никогда.
`Cache-Control` **не игнорируется** (кроме `Set-Cookie`): ответы `public, immutable`
кэшируются, `private, no-store` — нет.

**Кэш медиа на диске (в API)** — `src/services/media_cache.py`. Замер на прод-сервере:
S3 у провайдера отдаёт ~3 МБ/с (4 потока — ~8 МБ/с), локальный SSD — 500+ МБ/с,
поэтому после первого чтения файл остаётся на диске и отдаётся в ~80 раз быстрее.

- ключ объекта (`s3_key`) → файл `<MEDIA_CACHE_DIR>/objects/<key>`; «свежесть» —
  mtime, обновляется при каждом чтении;
- лимит `MEDIA_CACHE_MAX_BYTES` (по умолчанию 40 ГБ — вся библиотека ~8 ГБ) и
  `MEDIA_CACHE_MIN_FREE_BYTES` (10 ГБ): при превышении удаляются самые старые файлы (LRU);
- кэш **не общий**: права проверяет API на каждый запрос, поэтому кэшируются и
  премиум-оригиналы (в nginx-кэш их класть нельзя — утекут анонимам);
- запись бесплатная: при отдаче из S3 файл пишется в кэш «по пути» (`tee`, клиент
  ничего не ждёт), а парсер складывает в кэш уже скачанные оригиналы и построенные
  деривативы вместо удаления (доп. трафика нет);
- Range-запросы к видео обслуживаются с диска (`206` + `Content-Range`), при
  промахе объект догружается в кэш в фоне;
- в админке — карточка «Кэш медиа на диске»: объём/лимит/попадания, кнопки
  «Прогреть кэш» (все объекты из S3), «LRU-чистка», «Очистить».

**Безопасность**
- Пароли — PBKDF2-SHA256 (200k итераций), сессия — случайный токен в httpOnly-cookie
  `sid` (`SameSite=Lax`), в БД хранится только `sha256(токен)`.
- Админ-эндпоинты — `Authorization: Bearer <ADMIN_TOKEN>` (или `X-Admin-Token`).
- Бакет S3 приватный: клиент получает только same-origin URL нашего API.
- Секреты — только в `.env` (не коммитится; `extra="ignore"` в настройках, поэтому
  лишние переменные не ломают старт).

## 3. Модули

### 3.1 Парсер (`src/main.py`, `src/parsers/`, `src/services/scan_planner.py`)
- Демон всегда запущен; он идёт по **включённым источникам** (`sources.is_enabled`
  + флаг прогона `parser:{code}:enabled`, кнопка в админке источника); heartbeat
  `parser:{code}:up` / `:alive` / `:current` (TTL 45–60 с). Прогоны независимы:
  остановка одного источника не трогает остальные, ошибка одного не роняет демон.
- В проде **на каждый источник свой контейнер** из одного образа:
  `PARSER_SOURCE=dvach` / `PARSER_SOURCE=slivach` (см. `docker-compose.prod.yml`).
  Процесс трогает только свой источник, поэтому у контейнеров независимые
  рестарты, логи, лимиты (`deploy.resources.limits`) и расписание (`PARSE_INTERVAL`
  задаётся каждому свой). Без `PARSER_SOURCE` (локально) один процесс обслуживает
  все источники с адаптером. Сверку данных (reconciliation) ведёт ровно один
  контейнер: у 2ch `RECONCILE_MINUTES=60`, у остальных `-1`.
- **Адаптер источника** (`src/parsers/base.py`, реализация — `parsers/dvach.py`)
  знает только свой сайт: каталог → «треды» (`ThreadNode`) и файлы «треда»
  (`FileNode`, у 2ch с md5/размером до скачивания). Реестр адаптеров —
  `build_adapter(code)` в `src/parsers/__init__.py`. Есть два адаптера:
  - `dvach` — JSON-API 2ch (md5/размеры отдаёт API; `Referer` не нужен);
  - `slivach` — HTML сайта-источника (selectolax): категории → разделы
    (`slivach-<категория>`), записи-«сливы» → «треды», галереи → файлы.
    Особенности: **видео отдаётся только с `Referer`**, **md5 и размеров нет**
    (дедуп до скачивания — по `md5(url)`, `md5_synthetic`; валидатор не режет по
    весу, проверка — после скачивания), оригиналов нет (максимум webp ~2000 px и
    mp4), одна фотография лежит в нескольких размерах (оставляем самый крупный),
    а «отпечаток» записи (`fingerprint`) — имя обложки в карточке категории:
    по нему видно, что запись обновилась. Лимиты обхода — в `sources.config`:
    `boards` (категории), `max_pages`, `max_records`, `include_images`,
    `include_video`.
- **Планировщик** (`services/scan_planner.py`) — общий для всех источников:
  каталоги, очередь `pending_scan`, гигиена выпавших тредов, бюджет цикла,
  `round-robin` по доскам, инкрементальный проход, прогресс. «Треды» опознаются
  парой (доска, `external_id`): номер треда у 2ch, слаг записи у сайтов (для
  строковых id считается стабильный числовой суррогат — публичный API и фильтры
  по `thread_id` работают без изменений).
- Доски берутся из БД (`boards.parse_enabled`, порядок `sort_order`, только
  своего источника); `parse_mode` доски определяет, включать ли новые треды
  автоматически.
- Двухфазный цикл (чтобы ни одна доска не «залипала»):
  **фаза A** — дёшево обновляются каталоги всех парсируемых досок (1 запрос на
  доску) и помечаются треды `pending_scan` с причиной; **фаза B** — докачка по
  очереди из БД. Порядок очереди: «новый»/«изменения»/«файлы» (свежие файлы на
  форуме) → «просрочен»/«не скачивался», внутри групп — по «давности»
  сканирования (`last_scanned_at`, LRU). Очередь хранится в БД, поэтому
  перезапуск парсера её не теряет (курсор не нужен); тред, у которого
  `res/{id}.json` не прочитался, остаётся в очереди.
- Бюджет цикла и чередование досок: `PARSE_CYCLE_BUDGET_MINUTES` (дефолт 30) —
  после бюджета фаза B прерывается, остаток очереди продолжается в следующем
  цикле; внутри фазы B доски чередуются (round-robin), поэтому одна доска с
  длинной очередью не держит остальные.
- Параллельные загрузки: `MAX_PARALLEL_DOWNLOADS` (дефолт 2) — файлы качаются
  пачками, а обработка остаётся последовательной (одна сессия БД: валидация, S3,
  деривативы и запись идут по одному). Дедупликация выполняется **до** скачивания,
  поэтому в сеть уходят только отсутствующие файлы; `PREFETCH_MAX_BYTES` (64 МБ)
  ограничивает память — крупные файлы качаются по одному. При значении `1`
  поведение прежнее, с паузой `REQUEST_DELAY` между файлами.
- Обработка файла разбита на стадии: подготовка (фильтр → дедуп → скачивание →
  валидация → локальный файл) → выгрузка в S3 (+деривативы, без БД) → запись в БД
  (в SAVEPOINT, последовательно). Стадии 2–3 умеют идти конвейером
  (`MAX_PARALLEL_UPLOADS`), но **по умолчанию выключены**: замер показал, что
  одновременные выгрузки в наш S3-эндпоинт в 3 раза медленнее (10.9 МБ/с против
  3.0 МБ/с на объектах 8 МБ) — хранилище троттлит соединения, поэтому выигрыша
  нет. Включать `>1` имеет смысл только после замера на своём эндпоинте.
- Точечная сверка: перед проходом одним запросом берутся md5 уже сохранённых в
  треде файлов (`saved_md5_in_thread`), поэтому полный обход (догон, «недокачано»,
  «вручную») перебирает только отсутствующие файлы, а в итоге прохода видно
  «уже сохранено: N».
- Конвейер файла вынесен в отдельный модуль **`src/services/pipeline.py`**
  (`FilePipeline`): подготовка → S3 и деривативы → запись в БД. Логика не знает
  источника: она работает с метаданными, которые готовит адаптер, и о сайте знает
  только одно — заголовки скачивания (`download_headers`, у части сайтов без
  `Referer` файлы отдаются 403). `src/parsers/dvach.py` после разреза — 687 строк
  вместо 1153: в нём осталась специфика 2ch (JSON-API, маппинг) и оркестрация
  цикла (каталог, очередь, проход по треду). Следующий шаг — вынести оркестрацию в
  `services/scan_planner.py`, а из парсера сделать чистый адаптер источника
  (см. §9 «Мульти-источники», п. 2).
- Гигиена обхода (чтобы не было «забытых» тредов): тред, выпавший из каталога
  доски, получает `misses`/`missing_since` и гасится (`is_active=false`) только
  после `DEAD_THREAD_AFTER_MISSES` проходов подряд — обрезанный каталог 2ch
  больше не прячет живые треды; треды, которые давно не сканировались
  (`STALE_SCAN_HOURS`, дефолт 24 ч), попадают в очередь планового догона, а в
  админке видны чипами «В очереди»/«Просроченные»/«Мёртвые»/«Недокачано».
- `files_detected` («файлов на форуме») — это файлы, которые **мы должны были
  сохранить**: обновляется при каждом скане треда (без лишних запросов) и не
  включает мелочь, отброшенную правилами размера/разрешения (у 2ch у удалённых
  вложений остаются «заглушки» в 5–47 байт). Поэтому «Недокачано» — это реальные
  пропуски (битые файлы, ошибки сети/S3), а не шум: такие треды можно поставить
  в очередь кнопкой «В очередь».
- Дедупликация по `md5` из API до скачивания; файл, уже сохранённый **в этом же**
  треде, пропускается; для файла из другого треда создаётся строка-ссылка
  (`duplicate_of_id`, объект S3 переиспользуется). Если `md5` на форуме не совпал,
  но **SHA-256 контента** уже есть в БД (CDN пережимает картинки) — строка-ссылка
  создаётся по SHA-256: без этого вставка падала на `UNIQUE(media.file_hash)` и
  тред не мог пройти полный прогон.
- Запись файла идёт в SAVEPOINT, а ошибка одного файла не роняет тред и цикл:
  файл пропускается с `[err]`, тред остаётся в очереди и докачивается позже.
- Коммит БД после треда + каждые `DB_COMMIT_EVERY_FILES` файлов (дефолт 25);
  `last_scanned_at` обновляется только после полного прохода треда.
- Валидация: MIME (`python-magic`), размер, разрешение, целостность (md5 → SHA-256).
- Reconciliation: сверка БД ↔ S3 и локального кэша (период `RECONCILE_MINUTES`).

### 3.3 API (`src/api/`)
- Публичные роуты: `boards`, `boards/{slug}/threads`, `boards/{slug}/media`,
  `media/{id}` (+ `view`/`download`/`raw`/`asset/{kind}`), `feed`, `top`, `search`,
  `marks` («мои метки»), `auth/*`.
- Дубли-ссылки (`duplicate_of_id`) исключены из всех публичных выборок и счётчиков.
- Премиум-гейт: `thumb`/`web`/`video`/`raw`/`download` → 403 без подписки (401 анониму);
  публично доступен только размытый `thumb_blur`.
- Метка: `POST /media/{id}/mark` (переключатель, требует аккаунт); в списках
  отдаются `marks_count`, `marked` (по одному запросу на страницу).
- Админ-роуты (admin-токен): `overview`, `forum`, board CRUD + `reorder` + `delete`,
  `boards/{slug}/threads` (+`PATCH`, `bulk`), `scan` + `scan/status`,
  `backfill-variants` + `status`, `parser/start|stop`, `parser/status`,
  `cleanup-storage`, `reset`, `boards/{slug}/toggle`, `media/{id}/toggle`.
- Rate limiting на Redis: отдельные корзины для JSON-API (`API_RATE_LIMIT`, по умолчанию 300/мин)
  и медиа-файлов (`MEDIA_RATE_LIMIT`, 1500/мин), потоковая отдача медиа из S3
  (`S3Storage.open_object_stream`, чанки 256 КБ).

### 3.4 Frontend (`web/`, Next.js 14 App Router)
- Страницы: `/` (**главная — «витрина новинок»**: сводка архива, чипы Всё / Картинки /
  Видео / без подписки, фиксированные **24 карточки без автоподгрузки**, полка
  «Популярное сейчас» и чипы разделов), `/boards` (каталог разделов с фильтрами
  Все/Без подписки/Премиум — переехал с главной), `/new` (полный поток новинок:
  infinite scroll + фильтры), `/top`, `/board/{slug}` (треды → файлы треда),
  `/search`, `/media/{id}`, `/marks` («мои метки»; `/favorites` редиректит сюда),
  `/login`, `/profile`, `/admin`; `web/` standalone-сборка.
- Первый экран главной — медийный: над сеткой только две строки (название и цифры:
  файлов, тредов, +за сутки) и чипы фильтра, дальше сразу
  masonry. Полный поток — по ссылке «Смотреть дальше в полном потоке» (`/new`),
  правила компоновки — `docs/DESIGN.md` §4.0.
- SEO: `robots.txt` и `sitemap.xml` — маршруты Next (`app/robots.ts`, `app/sitemap.ts`);
  служебные страницы (`/admin`, `/profile`, `/login`, `/marks`, `/search`) закрыты
  `noindex`, публичные — с `canonical` и `metadataBase` (адрес из `SITE_URL`);
  фильтры/периоды канонизируются на «чистые» адреса. Микроразметка: `WebSite` +
  `SearchAction` на главной, `ImageObject`/`VideoObject` на страницах файлов.
- Каталог разделов: карточка — мозаика 2×2 свежих превью (`cover_thumbs` в
  `/api/v1/boards`, один запрос с оконной функцией), плитки со скелетоном до загрузки.
  Карточки автосортируются по числу файлов (крупные сверху, при равенстве — по слагу).
- «Продолжить просмотр»: при показе файла треда запоминается точка возврата
  (`lib/resume.ts`, localStorage `dredge.resume.v1` — 200 тредов, 60 дней), и в
  карточке треда появляется «смотрели файл N из M · когда» с кнопкой «продолжить»
  (открывает тред на этом файле) и ✕ «забыть»; «открыть все» всегда идёт с начала.
  Работает для анонима, но в браузере конкретного устройства (см. DESIGN §4.4c).
- «Новое с прошлого визита»: главная показывает `+N новых файлов с <дата> →`
  (ссылка на `/new?since=<ISO>`); момент визита — cookie `dv_last` (ставит
  `VisitStamp`, читает серверный рендер), фид фильтрует по `since`.
- Загрузка превью — blur-up: под `thumb` лежит размытый вариант (`blur_url` =
  `thumb_blur`), превью проявляется поверх; без размытого варианта — скелетон.
  Первые 6 карточек главной грузятся сразу (`eager`, `fetchpriority=high`) — LCP.
- Персональные флаги (метка `marked`, премиум `locked`) приходят с API во всех
  списках — лента, поиск, топ, превью тредов, карточка файла. SSR-запросы с
  пользовательскими cookie идут `cache: "no-store"`: Data Cache Next.js общий для
  всех, иначе чужой «лайк»/чужой премиум-статус попали бы в чужую страницу.
- Показатели: masonry-галерея + infinite scroll, карточки с бейджами
  (`ТОП`, `PREMIUM` 🔒/★, `НЕДОСТУПНО`), кнопка «метка» (🏷) поверх превью и в
  lightbox, маркер видео (значок ▶ + длительность) на карточках, превью тредов и
  в карусели просмотра, мобильная навигация (5 пунктов), `When`-время.
- Lightbox: перелистывание `←`/`→` **и колесом мыши** (порог + кулдаун, чтобы не
  проматывать пачками; Ctrl+колесо — зум браузера, над лентой миниатюр колесо не
  листает), **пробел — метка** «отличный контент» с плашкой-подтверждением,
  `Esc` — закрыть, клик по фону — закрыть.
- Премиум в UI: превью размывается (`blur` + 🔒), в lightbox вместо контента — CTA
  «Запросить доступ» → `/feedback?topic=premium`; при активной подписке превью открыто, бейдж ★.
- Лента (`/`, `/new`, страница раздела) раскладывается в колонки **на клиенте**
  (`components/Gallery.tsx`): раньше это делал CSS `columns`, и при догрузке браузер
  пересобирал всю сетку — уже показанные карточки «переезжали», правая часть
  ленты «заменялась». Теперь новые карточки докладываются в самую короткую колонку,
  а размещённые не двигаются. Догрузка идёт по курсору (`next_cursor`), поэтому
  появление новых файлов в архиве не сдвигает выдачу.
- Порядок в «треде»: список файлов идёт по `media.source_order` (порядок файла у
  источника, `post_num` из парсера), а не по времени скачивания. Тред читается с
  начала, новые файлы всегда попадают **в конец**; «Продолжить просмотр» ведёт к
  последнему просмотренному файлу (точка возврата — по id в localStorage) и
  показывает «+N новых в конце». В точке возврата хранится **размер треда**, а не
  размер загруженной порции: галерея грузится по 300 файлов (максимум API) и
  догружает следующие порции кнопкой или при листании до конца — иначе в треде из
  882 файлов «новых» насчитывалось 582 при нулевом приросте (формат точки —
  `dredge.resume.v2`, старые записи v1 удаляются при первом обращении).
- Порядок тредов внутри раздела выборный: `?sort=new` (по умолчанию, свежие),
  `?sort=files` (больше файлов в архиве — считается по видимым файлам треда),
  `?sort=posts`, `?sort=views`. Переключатель — чипы «порядок:» на странице
  раздела, выбор пишется в адрес (ссылка сохраняет порядок) без перезагрузки.
- Карточка треда показывает «+N» — сколько файлов треда добавилось с
  начала текущих отчётных суток (00:00 МСК) — и рядом «N в галерее» (всего файлов
  треда). Период тот же, что у «+N за сутки» на карточке раздела и в сводке на
  главной: сумма по тредам равна счётчику раздела (поле `media_today` в
  `/api/v1/boards/{slug}/threads`). Число файлов «в каталоге» (`files_count` —
  то, что заявляет источник в своём каталоге) в интерфейсе не показываем: оно
  бывает устаревшим и меньше фактического, а у сайтов-источников нулевое.
- Предупреждение 18+: модальное окно один раз в сутки (`components/AgeGate.tsx`),
  подтверждение — в cookie `dv_age` (`max-age=86400`, path=/). Разметка страниц от
  него не зависит, поэтому поисковики и режим без JS работают как раньше.
- Вход/выход: после входа и выхода вызывается `router.refresh()` (серверные
  компоненты) и событие `dredge:auth` (`lib/authEvents.ts`) — шапка обновляется
  сразу, без ручной перезагрузки страницы.
- Авторизация: `AuthMenu` в шапке (email → профиль, «Выйти»), `/login`
  (вход/регистрация), `/profile` (статус премиума, срок, активация на 1 день,
  счётчик меток со ссылкой на `/marks`).
- Брендинг: `Dredger` — «архив // отбор // доступ» (логотип в шапке, title/шаблон
  в `layout.tsx`, подвал), классы дизайн-системы `dredge-title` / `input-dredge`.

### 3.5 Админ-центр (`/admin`)
- Вкладка «Контент» идёт по реестру источников: у каждого своя вкладка, внутри —
  «Мои разделы» и список разделов источника («Доски форума» у 2ch, «Разделы
  сайта» у сайтов); парсер: «Запустить/Остановить», прогресс-бар по текущему
  треду (опрос 1 с), сводка по системе.
- Карточка доски: позиция в очереди (▲/▼), название (переименование), статистика
  (В БД / В S3 / Скачано / Пропущено / В каталоге / Видимых), переключатели
  `Парсить`, `published|unpublished`, `FREE|PREMIUM`, кнопка «Треды».
- Треды доски: чипы-фильтры, поиск по теме/номеру, «в работе» сверху, массовые
  операции (парсить/показать/PREMIUM/«вернуть в обход»), «Сканировать треды»
  (глубокий скан), прогресс-бар текущего треда.
- Гигиена обхода в списке тредов: чипы «В очереди» (ждут докачки),
  «Недокачано» (на форуме файлов больше, чем сохранено), «Просроченные»
  (парсинг включён, но тред давно не сканировался) и «Мёртвые» (тред выпал из
  каталога форума) со счётчиками; у треда видно причину очереди, дату последней
  попытки, а у мёртвого — дату исчезновения и число промахов; «вернуть в обход»
  сбрасывает `misses` и возвращает тред в публичные списки, «в очередь» —
  ручная постановка на докачку.
- Глобальные операции: «Оптимизировать медиа» (бэкфилл, «осталось N из M»),
  «Очистить S3», «Сбросить всё».
- Карточка «Кэш медиа на диске»: объём и лимит, попадания/промахи, свободное
  место, прогресс прогрева, кнопки «Прогреть кэш» (все объекты из S3),
  «LRU-чистка» и «Очистить» (опрос состояния — раз в 10 с).
- Добавление раздела: слаг проверяется по каталогу 2ch — если раздел удалён
  (форум отвечает 500/404), создание отклоняется с понятной причиной (в
  `index.json` 2ch остаются удалённые доски, например хентай-разделы `/h`, `/ho`).
- Карточка раздела показывает бейдж «каталог недоступен» с причиной, если
  последнее чтение каталога не удалось (писал парсер или кнопка «Сканировать
  треды»); статус живёт в Redis `board:catalog_error:{slug}`.
- Легаси-страница `/admin/boards/{slug}` (полный список тредов доски) осталась, но
  из UI больше не линкуется — управление тредами доступно в аккордеоне карточки.

- Список разделов источника (`GET /api/v1/admin/sources/{code}/catalog`) читает
  адаптер источника: у 2ch — `index.json`, у сайтов — категории из меню. Оттуда
  разделы добавляются в систему (`POST /admin/boards` со `source`), у выбранного
  раздела сразу видно, сколько файлов он уже отдал.

**Как забрать контент сайта (пример slivach).**

1. «Контент» → вкладка **slivach** → «Разделы сайта» → «Обновить список» →
   «Добавить» у нужных категорий (`slivach-modeli`, `slivach-asmr`, …).
2. «Мои разделы» → у раздела включить «Парсить» и нажать **«Загрузить записи»**:
   адаптер читает страницы категории и создаёт «треды» — записи-«сливы».
   Они создаются **выключенными** (`parse_mode=selected`), медиа не качается.
3. В аккордеоне раздела включить «Парсить» у нужных записей (поштучно или
   массово чекбоксами), при необходимости выставить «published» / «премиум».
   «Загрузить записи» с галкой глубокого скана сразу показывает «файлов: N».
4. «Запустить прогон» → парсер скачает файлы выбранных записей (фото и видео),
   прогресс и журнал — на карточке раздела и в `/admin/sources`.

Лимиты обхода задаются в конфиге источника (`/admin/sources`): `max_pages`
(0 — вся пагинация категории), `max_records` (0 — все записи), `include_images`,
`include_video`. Объём регулируется в первую очередь тем, какие записи включены,
и бюджетом прогона (`budget_minutes`).


### 3.6 Отчётный период, ежедневный отчёт и обратная связь

**Отчётные сутки — по Москве**: с 00:00:00 до 00:00:00 МСК (`MSK_OFFSET +3`,
переходов на летнее время нет). Границы считает `services/reporting.py`
(в БД время хранится в UTC, поэтому период переводится в UTC). Один и тот же
период используется всюду, где написано «за сутки», — цифры совпадают:

- сводка на главной (`GET /api/v1/status` → `files_today`, `period_label`);
- карточка раздела в каталоге (`GET /api/v1/boards` → `media_today`, «+N за сутки»);
- админка и ежедневное письмо-отчёт.

**Ежедневный отчёт на почту.** Считается за прошедшие сутки и уходит сразу после
00:00 МСК (+`DAILY_REPORT_DELAY_MINUTES`, чтобы парсер дописал прогон). Состав
задаётся `DAILY_REPORT_MODE`:

```
short     Добавлено файлов 487 в 14 тредов в 2 разделах. Уникальных посетителей: 58.
standard  то же + контент (картинки/видео, объём, топ разделов),
          посетители (уникальные/новые, просмотры, сессии), активность
          (новые аккаунты, метки, прогоны парсера: успешных/с ошибками)
full      то же + ошибки прогонов (для отладки)
```

Адресаты — `DAILY_REPORT_EMAILS`, иначе `ADMIN_EMAILS`. Текст можно посмотреть
без отправки: `GET /api/v1/admin/reports/daily?period=yesterday` (и отправить
вручную — `POST /api/v1/admin/reports/daily/send`).

**Обратная связь** (`/feedback`, ссылка в подвале и в профиле). Темы: баг, идея,
премиум-доступ, контент, другое. Обращение сохраняется в таблицу `feedback` и
письмом уходит админам (отправка фоном — посетитель не ждёт SMTP). В админке
заявки лежат во вкладке «Обратная связь»: фильтры по статусам
(`new → in_progress → answered → closed`), поиск, заметка-ответ, удаление.
Премиум-доступ включает админ вручную (`/admin/users`), посетитель лишь
отправляет заявку.


## 4. Доступ: роли, метки и премиум

**Матрица ролей**

| Роль | Может | Не может |
|---|---|---|
| Аноним | просмотр доступного контента (включая размытые превью премиума), лента, топ, поиск | метки, скачивание, оригиналы, полные премиум-файлы |
| Зарегистрированный | всё как аноним + метки + размытые превью премиума | скачивание, оригиналы, полные премиум-файлы |
| Премиум | всё как зарегистрированный + премиум-разделы + скачивание + оригиналы | — |

Реализация: `require_user` (метки, профиль) и `require_premium`
(скачивание и оригиналы: аноним → 401, без подписки → 403). Статус подписки —
`users.premium_until`, а включает премиум **администратор** вручную —
`POST /api/v1/admin/users/{id}/premium` (вкладка «Пользователи»). Самостоятельной
активации из профиля нет: посетитель отправляет заявку с темой «Премиум-доступ»
через форму обратной связи (`/feedback`), админ её видит и включает доступ.

**Правила премиума**
- `boards.is_premium = true` → закрывает **все** треды доски (в админке у тредов
  переключатель PREMIUM блокируется с пометкой «унаследовано от доски»);
- `threads_state.is_premium = true` → закрывает конкретный тред;
- эффективный признак дублируется в `media.is_premium` (синхронизируется при смене
  флагов и проставляется парсером для новых файлов);
- без подписки `GET /api/v1/media/{id}/asset/{thumb|web|video}`, `/raw` и
  `/download` дают **403** (анониму — 401), а `thumb_blur` отдаётся всегда
  (публично, кэшируется);
- в UI: бейдж 🔒 `PREMIUM` + blur + CTA, если подписки нет; бейдж ★ `PREMIUM`
  **без** blur, если подписка активна — видно, где премиум, но нет сигнала «закрыто».

**Метка** (требует аккаунт) — единая пользовательская отметка файла:
- переключатель `POST /api/v1/media/{id}/mark` → `{marked, marks_count}`;
- публичный счётчик `media.marks_count` учитывается в `popularity_score`
  (`views*0.3 + downloads*0.7 + marks*1.5`) и доступен как сортировка `sort=marks`;
- личный список «мои метки» — `GET /api/v1/marks` (страница `/marks`, пункт «Метки»
  в шапке и мобильной навигации, ссылка из профиля);
- отдельного «избранного» нет — оно объединено с метками (миграция `p1q2r3s4t5u6`),
  старый адрес `/favorites` редиректит на `/marks`;
- в интерфейсе: 🏷 метка на карточке и в lightbox, **пробел** — быстрая метка
  в просмотре файла (+ плашка-подтверждение), счётчик меток в профиле.

## 6. База данных (PostgreSQL, Alembic)

- **sources**: `id, code (unique), title, kind (json|html), base_url, config (JSONB),
  is_enabled, schedule_minutes, rate_limit_rps, budget_minutes, sort_order, created_at,
  updated_at` — реестр источников контента; прогон каждого независим (`parser:{code}:*`)
- **boards**: `id, slug, title, description, is_visible, parse_enabled, is_premium,
  parse_mode (all|selected), sort_order, source_id, created_at, updated_at`
- **threads_state**: `board_id, thread_id, external_id (номер 2ch / слаг записи),
  fingerprint (метка изменения у источника), subject, comment, thread_timestamp,
  posts_count, files_count, files_detected,
  views_count, last_scanned_at, is_active, parse_enabled, is_visible, is_premium` —
  уникально `board_id + thread_id` и `board_id + external_id`
- **media**: `id, board_id, thread_id, source_id, original_name, source_url, source_md5,
  file_hash (sha-256), file_size, mime_type, media_type (image|video), s3_bucket,
  s3_key, local_path, width, height, variants, duration_seconds, is_premium,
  download_status, is_visible, is_active, duplicate_of_id, views_count,
  downloads_count, marks_count, popularity_score, created_at, updated_at`
- **parse_runs**: `source_id, started_at, finished_at, status (running|ok|error|stopped),
  phase, stats (JSONB), error` — история прогонов источника (админка: вкладка источника)
- **view_stats / download_stats**: `media_id, ip_hash, viewed_at/downloaded_at`
  (дедуп статистики по IP за 24 ч)
- **media_marks**: `user_id, media_id, created_at` (UNIQUE user+media) — метка
  «отличный контент»: и публичный счётчик, и личный список «мои метки»;
  счётчик дублируется в `media.marks_count`
- **users**: `id, email, password_hash, is_active, premium_until, created_at`;
  **sessions**: `user_id, token_hash, expires_at`

Значения:
- `download_status`: `new` → `downloaded` (лежит локально, не выгружен) →
  `uploaded` / `verified` (в S3) либо `missing` (файл потерян).
- `media.variants` (JSON): `thumb`, `thumb_blur`, `web` (для видео — `video`)
  → ключи объектов в S3.
- `duplicate_of_id`: файл-ссылка на уже сохранённый оригинал (тот же `md5` в другом
  треде/доске). Дубли не считаются в статистике и не показываются в галереях.
- `marks_count` и `popularity_score`: индекс популярности =
  `views_count * 0.3 + downloads_count * 0.7 + marks_count * 1.5`.

```sql
-- состояние очереди парсера (что ещё не скачано)
select count(*) filter (where last_scanned_at is null) as not_scanned,
       count(*) filter (where is_active and parse_enabled) as parsing
from threads_state where board_id = $1;

-- сводка по файлам доски (без дублей) — как в админке
select count(*) filter (where duplicate_of_id is null) as files,
       count(*) filter (where duplicate_of_id is null and download_status in ('uploaded','verified')) as in_s3,
       count(*) filter (where duplicate_of_id is not null) as dup_links
from media where board_id = $1;

select count(*) from media
where s3_key is not null and (variants is null or variants->'thumb_blur' is null);
```

## 8. Эксплуатация и деплой

Подробная инструкция — [`../DEPLOY.md`](../DEPLOY.md). Кратко:

- запуск: `cp .env.prod.example .env` → заполнить `S3_*` и `ADMIN_TOKEN` →
  `docker compose -f docker-compose.prod.yml up -d --build`;
- обновление кода: `git pull && docker compose -f docker-compose.prod.yml up -d --build`
  (помните про общий образ `parser-backend` — §2);
- миграции применяются сервисом `migrate` при старте; текущая голова —
  `t5u6v7w8x9y0`;
- проверка после выкатки: `X-Cache-Status` у `thumb_blur` (`MISS → HIT`), 403 у
  премиум-`web` без подписки, 401 у `/raw` без сессии;
- SEO и заголовки: `robots.txt`/`sitemap.xml` отдаются, `SITE_URL` задаёт canonical
  и адреса в микроразметке; в ответах нет версии nginx (`server_tokens off`) и
  `X-Powered-By` (`poweredByHeader: false`), `www` → `301` на основной домен;
- обязательные переменные парсера: `DB_COMMIT_EVERY_FILES` (дефолт 25),
  `REQUEST_DELAY`, `PARSE_INTERVAL`, `MAX_FILE_SIZE`, `RECONCILE_MINUTES`;
- резервные копии: `pg_dump` + версионирование бакета S3 (см. `DEPLOY.md`);
- диагностика: застрявшие ключи `parser:progress` / `backfill:variants` со статусом
  `running` после аварийного рестарта → `docker compose exec redis redis-cli del …`.
