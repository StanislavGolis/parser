# Dredger 2.0 — план работ до продакшена

Документ отвечает на вопрос «что осталось сделать, чтобы открыть продажи». Составлен
по факту аудита боевого сервера **15.09.2026** (что реально включено, что лежит в БД,
что настроено в `.env`) — не по предположениям. Дополняет
[`Dredger 2.0 — план перехода.md`](Dredger%202.0%20—%20план%20перехода.md)
(фазы и порядок) и [`README.md`](README.md) (техническая документация).

**Обозначения:** `[x]` — сделано и проверено на проде · `[ ]` — осталось ·
`[~]` — сделано частично (есть код, нет финального шага).

лимит файлов не нужен, разделение идёт по разделам.

- [x] **Модель Free реализована и проверена на проде (15.09.2026)**: Free смотрит

### 1.3 Оплата (крипта, без эквайрингов)
- [x] Ручная выдача тарифом: `/admin/plans` → «Выдать тариф вручную» (пишет в журнал
      `payments` со скидкой и пометкой) и старая ручка `POST /api/v1/admin/users/{id}/premium`.
- [x] Журнал оплат `payments`: тариф, сумма, скидка, провайдер, статус, срок, кто.
- [x] Идемпотентность заложена: `register_payment` создаёт счёт `pending`, `mark_paid`
      выдаёт премиум ровно один раз (повторный вебхук не продлевает подписку дважды).
- [x] **Оплата звёздами Telegram** (Bot Payments, `currency: XTR`): бот показывает кнопки
      «<тариф> — N ⭐», выставляет счёт, подтверждает `pre_checkout_query`, а после оплаты
      зовёт `POST /api/v1/billing/stars`. Провайдер не требуется — только токен бота.
- [x] **Инцидент 15.09.2026 (исправлен)**: первый тестовый платёж не зачислился —
      `INSERT` в `payments` падал с `value too long for type character varying(64)`:
      у Stars `telegram_payment_charge_id` длиннее 64 символов. Лечение: миграция
      `f3a4b5c6d7e8` расширила `payments.external_id` до 255, бот пишет оплату в лог и
      делает вторую попытку, а если аккаунта по `telegram_id` ещё нет — создаёт его,
      чтобы оплата не потерялась. Проверено на проде: зачисление 200, повторный вызов
      не продлевает подписку дважды (идемпотентность).
      **Потерянный платёж восстановлен**: запись #3 в `payments` (`provider=stars`,
      тариф `days3`, 25 ⭐, пометка «восстановлено вручную»), премиум аккаунта 17
      продлён на 3 дня. Теперь журнал сходится с балансом бота: 2 оплаты ↔ 50 ⭐.

**Как сверять продажи со звёздами (если снова будут сомнения).**
Звёзды живут на балансе бота в Telegram, у нас — в `payments`. Сверка:

```bash
# 1) сколько звёзд пришло боту
docker compose -f docker-compose.prod.yml exec -T api python -c \
  "import asyncio,os,aiohttp; ..."   # или: скрипт check_stars_balance.sh из бэкапов
# проще: python-однострочник из C:\Users\Stas\dredge-backups\check_stars_balance.sh
# 2) сколько оплат и на сколько звёзд у нас
docker compose -f docker-compose.prod.yml exec -T postgres \
  psql -U parser -d parser -c "SELECT id, plan_code, status, note FROM payments ORDER BY id"
```

Расхождение («у бота больше звёзд, чем в журнале») означает, что оплата пришла, а
зачисление упало — смотрим `docker compose logs telegram-gateway | grep -i "Оплата звёздами"`
(там `payload`, `stars`, `charge_id`) и `logs api | grep billing`, после чего зачисляем
запись вручную с пометкой «восстановлено вручную».
- [x] **Страница тарифов на сайте (15.09.2026)**: `/subscribe` — витрина в звёздах
      (карточки 3 дня / месяц / год / навсегда, акция с названием и описанием), блоки
